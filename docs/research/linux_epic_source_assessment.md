**Verdict: FEASIBILITY ONLY.** Static repository audit plus an attempted native Linux compile, blocked at dependency retrieval before compilation. Linux runtime, tests and Epic-file comparisons remain **NOT RUN**. No Epic installation is confirmed. Only documentation was changed; no source installation, runtime code or tests were changed. Scope: KH2FM only, not other collection games. Acceptance record: [T171](../tasks/T171_linux_epic_feasibility.md).

## Bottom line

A native Linux rewrite using legally supplied Windows game files is architecturally plausible, but neither Linux support nor Epic compatibility is established. Linux host portability and Epic source qualification are separate workstreams. This is not simply removing a Steam check, and it does not complete the game's outstanding fidelity work.

The current contract specifies Windows x86_64 MSVC and selected Steam source, with native saves required and vendor import undecided (`docs/fidelity-contract.md:10-29`). Linux/EGS release acceptance would need an explicit contract extension. Latest development-camera results still lack controlled installed/rewrite comparisons (`docs/tasks/T170-lock-camera-and-scan-gauge.md:123-137`).

## Audited boundaries

### Source identity is content-based, but the profile is Steam-shaped

- `validation::required_files()` fixes one executable and six HED/PKG pairs under `Image/dt` (`validation/src/lib.rs:228-240`). `scan_with()` / `scan_counted()` read and hash them, optionally take matching Steam app metadata as clues, and **always** emit `quarantined_unqualified`; the manifest explicitly says no independently qualified supported-build profile exists (`validation/src/lib.rs:247-251`, `validation/src/lib.rs:271-329`). No Steam metadata is required to produce this candidate manifest; that is not Epic qualification.
- `content_identity(files: &[SourceFile]) -> String` binds relative names, lengths and hashes, excluding root paths and timestamps (`validation/src/lib.rs:213-226`). An Epic executable difference changes the aggregate identity even if packages happen to match. Hash equality with a locally recorded candidate establishes consistency, not vendor authenticity or edition equivalence.
- `ProbeSource::bind()` validates the manifest's canonical root, layout, internal identities and quarantine label (`source/data/src/probe_source.rs:142-186`). `verify_session()` rehashes executable/index files, checks package size/time, and relies on per-read chunk verification for schema 2; schema 1 falls back to a full scan (`source/data/src/probe_source.rs:233-285`). `SourceReader::chunk()` rejects mismatched package bytes (`source/data/src/probe_source.rs:78-103`). Retain this session boundary for both storefronts; remembered paths and launcher checks are insufficient.

### Launcher “supported” is not an edition certification

- `quick_check()` uses `quick_match()` size/time checks, not fresh content hashing (`source/main/src/launcher/install.rs:215-237`, `source/main/src/launcher/install.rs:257-272`). `supported_identity()` reads the title configuration's identity (`source/main/src/launcher/install.rs:612-617`); `checked()` rejects a mismatch **only when that optional identity exists** (`source/main/src/launcher.rs:741-778`). This is a development-config restriction, not a qualified storefront/build allowlist.
- `test_args()` requires configuration identity to match the bound source, with generated configs as a fallback (`source/main/src/launcher/install.rs:667-724`). Direct `play_args()` still uses the `steam_root` launch-file field (`source/main/src/launcher/install.rs:741-755`). The title independently checks config identity and calls `verify_session()` (`source/main/src/title.rs:809-814`). Consistent config/source bytes must not be mistaken for approved edition semantics.

### Package reading can likely be reused, subject to actual Epic evidence

`ProbeSource::open_index()` opens HED/PKG files read-only, bounds paths to the selected root and calls `read_hed()` (`source/data/src/probe_source.rs:295-365`). `read_original<R: Read + Seek>()` and `read_original_limited()` operate on byte streams with indexed-range and size checks (`source/data/src/original_payload.rs:66-120`). These are good reuse candidates on Linux. Their existence proves neither identical Epic layouts/encryption/replacements nor shared language, movie, audio or edition behavior. Actual Epic files must determine reuse versus profile-specific decoding.

Reading the Windows executable is **not executing it**: the validator hashes bytes; `Sbox::from_executable(exe: &[u8])` parses PE sections to obtain a table (`source/game/save/src/cipher.rs:39-77`). Native rewrite launches use `Command::new(exe)` for the rewrite/current executable or its viewer siblings, not the installed KH2 executable (`source/main/src/launcher.rs:400-431`). These paths do not inherently require Wine/Proton. Running the original for future reference comparisons is a separate concern.

## Save/account caveats

The current save backend is not storefront-neutral. `Store::new(path, steam_id, sbox)` derives a Steam-account key; `Store::save()` can write its supplied path, so read-only vendor handling is a caller responsibility (`source/game/save/src/store.rs:60-99`). `original_folder()` searches Windows Documents/OneDrive Steam folders, and `steam_ids()` parses numeric account directories (`source/game/save/src/store.rs:103-133`).

`FileBackend::open()` reads the executable table, chooses the first discovered Steam ID (or zero), stores the rewrite container at one shared `data_dir/saves` filename, and automatically seeds it from a vendor save when no private copy exists (`source/main/src/save_files.rs:43-70`). Thus account/source switching can collide or fail to decrypt; Linux's absent Windows folders does not remove the executable-table dependency. `key_from_steam_id()` uses MD5 of the decimal ID plus a suffix (`source/game/save/src/cipher.rs:93-98`). None of this establishes Epic account/key compatibility. Make import explicit and separate from native save creation; do not treat generic container-mask recovery as Epic-format proof.

## Shortest route and effort boundary

1. Establish a reproducible Linux build of the current development target using the existing Steam candidate, without changing source-admission rules. Resolve dependency retrieval, enable a Linux window backend, then address launcher fonts/paths and audio. A successful smoke window is an environment check, not qualified gameplay.
2. With a user-selected existing Epic install, privately inventory and compare KH2FM executable/package identities, archive structures, original/replacement payloads and executable-derived tables. Keep it quarantined until a supported profile is qualified. Manual folder selection is the first useful integration; an Epic launcher, Heroic or Legendary discovery adapter can follow and must not become proof of compatibility.
3. Once qualification permits it, verify a source-bound scene, input, audible playback, save/load, source-change rejection and source/cache isolation on Linux. Add Linux CI and packaging checks while retaining the Windows/Steam path. Controller, GPU and Wayland/X11 coverage need explicit tested configurations.

This is a host-platform port plus a second data-source profile, not necessarily a second game engine. The Linux gaps are concrete and bounded; the Epic effort cannot be responsibly estimated before its files are inspected. If its relevant payloads and executable-derived tables are compatible, much of the importer can be reused. Differences require profile-specific decoding and, where behavior differs, additional reference research. Neither workstream completes the unfinished campaign/fidelity roadmap. Native execution of the rewrite should not require Wine/Proton; running the original Windows game for controlled comparisons is separate.

This supports the feature-selection finding, not a claim that this application builds or runs. Repository code is the primary evidence for the audio/font/path/save findings above. No Epic runtime or archive compatibility is inferred from third-party tool documentation.
