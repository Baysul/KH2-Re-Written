# T133 — Enemy AI from the executable's own scripts

Owner Claude, 2026-10-16, requested by burba in the project thread. Gate: enemy AI
(not passed). Prerequisites: T125 (Dusk and Soldier approximations), the Steam
build 15194255 executable analysis kept in private local storage. Build identity:

read only; no writer or mod manager was launched against it.

## Steps and evidence

1. New crate `source/game/enemy`: an interpreter for the object scripts (BAR type 3
   in `obj/<model>.mdlx`) with the executable's thread tree, act manager, slot/tag
   memory model, RNG order and call-by-trap interface. Each translated routine names
   its executable address in a comment. Evidence: the private spec and decompile
   notes under `research/enemy-ai-20261016` in local storage; nothing from them is in
   Git.
2. About 300 built-in script functions are implemented across the tables: math,
   object, target, system, battle sheet, attack objects, routine flags and the small
   state setters. A function with no implementation is recorded and, in development
   only, reads as zero; it is never guessed. Functions whose engine service is not
   translated (effects, lights, camera, sound, magic, mission HUD, hooks, grabs, the
   hop and hover physics modes) are implemented as recorded stubs that return zero
   or a placeholder handle; those are listed as [U] in the code comments.
3. Motion events: the range and frame event dispatchers and the per-tick flag reset
   are translated from the executable into `enemy::motion`. The frame order follows
   the executable: motion advance and events, then the script, then root motion and
   physics. Take-off enters the pending jump or fly mode.
4. Physics mode 5 (`obj_fly`): the steering step FUN_1403b7ad0 and its mode routine
   FUN_140421c80, with the executable's two-frame sampling.
5. Attack objects (`YS::ATTACK`): state, flag words and the table 2 attack functions
   in `enemy::attack`. The per-frame hit test against Sora and the damage it applies
   are not translated; hit flags stay clear until a host sets them.
6. Two engine bugs found by comparing the script brain's act order with the
   default Dusk brain, both fixed: the motion end pulse carried over into a newly
   started motion (every act finished at once), and script vectors have +Y down in
   the executable, which scripts use to name `down`, test landing and probe the
   ground; the engine keeps +Y up and flips y at the trap boundary.
6a. Sora is reachable from scripts through a proxy object, so every function that
   takes an object also works on the player (position and heading follow the host).
7. Test-room hook: `KH2RW_ENEMY_AI=script` runs actors through this engine
   (`source/main/src/test_room/enemy_script.rs`). The default brain is unchanged.
8. Synthetic tests cover the interpreter, act manager, motion flags, steering,
   attack objects, vector math and the small functions. They use generated bytes
   only.

## Uncertainty

- Target-record word +0 returns the object handle even when the id is a battle
  target table id.
- Sheet pools above the first and the element-rate index mapping are unconfirmed.
- Frame event routines for sound, effect and camera kinds are reported to the host,
  not executed.
- `vector_rotx` and `vector_rot` assume the usual rotation matrix; the vendor
  matrix builder was not read.
- The damage record's `exec_damage_*` functions are recorded only; the engine's
  default reaction already ran when the hit was taken.
